# 도메인 규칙 기록

재설계로 코드를 다시 쓰더라도 잃으면 안 되는 **판단의 기록**이다. 화면과 무관하게 유지해야 하는 규칙만 담는다.

추출 시점: `pre-redesign` 태그 (클라이언트 85파일 23,759줄, 마이그레이션 36개 5,365줄).
각 항목의 원본 위치를 함께 적었으니 필요하면 태그에서 꺼내 볼 수 있다.

## 불변 원칙

새로 만들어도 반드시 지켜야 한다. 출처는 `AGENTS.md`와 각 마이그레이션의 RLS 정책이다.

- 정확한 위도·경도는 저장하지 않는다. 지역(동네) 단위 정보만 다룬다.
- `public` 스키마의 모든 테이블은 RLS를 켜고 실제 접근 모델에 맞는 정책을 둔다.
- 클라이언트에 `service_role`이나 secret key를 노출하지 않는다.
- 사용자는 다른 사용자의 관찰·후보 행을 읽거나 수정할 수 없다.
- 공개 고양이와 공개 동네 기록만 후보 데이터의 입력으로 쓴다.
- 사진만으로 동일 개체를 자동 확정하지 않는다. 사용자 확인을 거친다.
- 생성형 AI나 외부 유료 AI API를 도입하지 않는다(온디바이스만).

## 희귀도 산정

출처: `000017_cat_rarity_rules.sql`

**털색별 기본 희귀도**

| 털색 | 기본값 |
|---|---|
| 치즈냥 | 2 |
| 흰냥 | 2 |
| 턱시도 | 3 |
| 검은냥 | 3 |
| 삼색이 | 4 |
| (그 외) | 3 |

**희소성 보정** — 기본값에 아래를 더하고 1~5로 클램프한다.

- 동네 기준: 그 동네에 고양이가 3마리 이상인데 해당 털색 기록이 0이면 +1. 8마리 이상인데 해당 털색이 1마리 이하면 +1.
- 전역 기준: 전체 고양이가 10마리 이상일 때, 해당 털색 비중이 12% 미만이면 +1.
- 표본이 부족하면(동네 미매칭, 전체 10마리 미만) 보정 없이 기본값을 쓴다.

산정 근거는 `cats.rarity_reasons`에 사람이 읽을 문장으로 함께 저장한다. **숫자만 주지 않고 이유를 설명하는 것이 이 규칙의 핵심 의도다.**

## 동네 리더보드 점수

출처: `000024_neighborhood_leaderboard.sql`

하루·유저·고양이 단위로 묶은 뒤 점수를 매긴다.

- 그 유저가 그 고양이를 **처음 만난 날**이면 3점, 아니면 1점
- 사진이 있으면 +1점

정렬은 기여 점수 → 수집 고양이 수 → 기록 수 → 닉네임 순이다. 같은 날 같은 고양이를 여러 번 찍어도 하루 한 번으로 집계해 **연타를 막는 것이 의도**다.

## 동일 개체 매칭 점수

출처: `000034_visual_embedding_and_unified_scoring.sql`. 배경은 `cat-identity-matching.md` 참조.

후보 풀은 현재 동네에 기록된 고양이 전체다. 점수는 아래 합이며 0.99에서 클램프한다.

| 신호 | 배점 |
|---|---|
| 기본점 | 0.30 |
| 내 도감에 이미 있음 | +0.15 |
| 지역명 정확 일치 | +0.10 (부분 일치 +0.05) |
| 털색 힌트 일치 | +0.08 |
| 최근성 30일 이내 / 180일 이내 / 그 외 | +0.15 / +0.10 / +0.05 |
| 동네 기록 횟수 | min(n, 20) × 0.005 |
| 시각 임베딩 코사인 유사도 | × 0.25 |

**재설계 시 반드시 재검토할 것** (분석 결과 확인된 문제)

1. 사진 신호(최대 0.33)가 메타 신호(최대 0.40)에 묻힌다. 닮은 고양이보다 자주 본 고양이가 위로 올라간다.
2. 대표 임베딩이 최신 확정 관찰 1장으로 덮어써져 나쁜 사진 한 장이 기준 벡터를 오염시킨다. 여러 기준 사진 평균으로 바꿔야 한다.
3. `embedding_version` 불일치 시 유사도가 null → `coalesce(...,0)`으로 0점 처리된다. **비교 불가와 안 닮음이 구분되지 않는다.**
4. iOS `VNGenerateImageFeaturePrint`는 범용 이미지 유사도이지 개체 재식별 모델이 아니다. 개체 판별력은 검증되지 않았다.
5. Android 임베딩이 없어 플랫폼 간에 같은 고양이를 잇지 못한다. → 아래 "임베딩 결정"에서 크로스플랫폼 통일로 정리했다.
6. 후보 풀에 상한이 없어 동네 개체가 많아지면 느려진다.

측정을 하려면 `cat_match_candidates`에 `visual_similarity`를 저장해야 한다. 지금은 점수 계산에만 쓰이고 남지 않아 임베딩 신호만 따로 평가할 수 없다. **소급이 불가능하므로 새 스키마에는 처음부터 넣는다.**

## 관찰 생명주기

출처: `20260712083111_cat_identity_candidates.sql`, `000033_stale_observation_cleanup.sql`

```
촬영 → cat_observations(status='pending')
     → 후보 생성(generate_cat_match_candidates)
     → 사용자 확인
        ├ 동일 개체 → status='linked', resolved_cat_id 설정
        ├ 새 고양이 → status='new_cat'
        └ 불확실   → cat_sightings(미확인 목격)
     → 3일간 pending이면 status='expired' + 후보·이미지 정리(cron)
```

- 정리 대상은 `pending`뿐이다. 확정된 관찰과 그 후보 행은 보존한다.
- 이미지는 사용자 폴더의 `observations/` 경로만 지운다. 확정된 사진은 다른 곳에서 참조된다.
- 관찰이 확정되면 트리거가 개체의 대표 임베딩을 갱신한다.

**보존이 중요한 이유**: 확정된 관찰의 후보 행이 남아 있어야 나중에 매칭 정확도(Top-1, Recall@k)를 소급 측정할 수 있다.

## 온디바이스 비전 계약

CatVision 네이티브 모듈은 `catdex-client/modules/cat-vision`에 다시 만들었다. TS 브리지는 `src/shared/native/catVision.ts`다. 플랫폼별 구현은 다르지만 **반환 계약과 여백 비율(0.18)은 동일하게 유지**한다.
털색·무늬 판정은 네이티브가 아니라 JS(`features/capture/coat/coat-analysis.ts`) 한 곳에서 한다. 그래야 플랫폼 간 판정이 어긋날 수 없고, 임계값을 재빌드 없이 조정할 수 있다.

| 플랫폼 | 고양이 탐지 | 누끼 |
|---|---|---|
| iOS | `VNRecognizeAnimalsRequest` | `VNGenerateForegroundInstanceMaskRequest` (iOS 17+) |
| Android | ML Kit Image Labeling (번들 모델) | ML Kit Subject Segmentation (Play 서비스, 최초 1회 다운로드) |

**네이티브 모듈 반환값**

| 필드 | 용도 |
|---|---|
| `hasCat`, `confidence` | 고양이 탐지 여부와 신뢰도 |
| `boundingBox` | 좌상단 원점으로 정규화된 표시용 경계 상자 |
| `cutoutImageUri`, `cutoutWidth`, `cutoutHeight` | 누끼 PNG(캐시 디렉터리)와 크기 |
| `isPreciseCutout` | 마스크 기반이면 true, 사각 크롭 폴백이면 false |
| `subjectSamples` | 잘라낸 피사체 픽셀 격자 128×128 RGBA(base64). 털색·무늬 판정 입력 |
| `sceneSamples` | 원본 색 + 피사체 마스크(알파) 64×64. 알파 없는 픽셀이 배경이라 조명 추정에 쓴다 |
| `embedding`, `embeddingVersion` | **현재 비어 있다.** 아래 결정 참고 |

`featureVector`(신뢰도·상자 크기·해상도)는 개체 구분에 쓸 수 없어 계약에서 뺐다.

**폴백 순서**: 정밀 마스크 → 탐지 상자(또는 마스크 커버 영역) 사각 크롭 → 원본. 어느 단계든 촬영 흐름은 끊기지 않고, 정밀도는 `isPreciseCutout`으로만 구분한다.

### 임베딩 결정 (2026-07-27)

**기존 `vn-fp-*` 임베딩을 폐기하고, 두 플랫폼이 같은 모델을 쓰는 방식으로 다시 만든다.**

- 근거: `VNGenerateImageFeaturePrint`는 iOS 전용이라 Android 유저와 같은 고양이를 이을 수 없다. 위 "동일 개체 매칭 점수" 5번 문제의 원인이며, 어느 쪽을 남겨도 플랫폼 하나는 버려야 한다.
- 따라서 **기존 `cats.embedding` / `cat_observations.embedding` 값은 재사용하지 않는다.** 새 모델을 붙일 때 컬럼을 비우거나 새 버전 문자열로 갈아 끼운다.
- 새 모델을 붙이기 전까지 네이티브 모듈은 `embedding: []`, `embeddingVersion: null`을 반환한다. 임베딩 없이도 촬영·누끼는 정상 동작한다.
- 후속 작업: 공용 모델(TFLite/ONNX 등) 선정 → 양 플랫폼 추론 경로 구현 → 새 `embedding_version` 문자열 규칙 확정 → 누끼 이미지 기준 임베딩인지 원본 기준인지 확정. 마지막 항목은 매칭 정확도를 좌우하므로 모델 선정과 함께 결정한다.

### 털색 결정 (2026-07-27)

**"고등어냥" 같은 합성 라벨을 버리고 색(다중 선택)과 무늬(단일 선택) 두 축으로 나눈다.**

색 9종: 검정 / 회색(Gray·Blue) / 갈색 / 초콜릿 / 시나몬 / 주황(Orange·Red) / 크림 / 라일락 / 흰색
무늬 4종: 원톤 / 투톤 / 태비 / 토티

**자동 판정은 사전 선택까지만 한다.** 확신이 부족하면 비워서 사용자가 고르게 한다. 틀린 값을 우기는 것보다 낫다.

**색 — 어디까지 믿을 수 있나**

검정·흰색·회색·주황·갈색은 명도와 채도 차이가 커서 조명이 흔들려도 유지된다. 반면 **초콜릿·시나몬·라일락·크림은 야외 조명에서 신뢰할 수 없다**. 갈색 계열끼리 색조 차이가 10~20°에 불과하고, 라일락은 화이트밸런스가 정확해야만 회색과 구분되며, 크림은 따뜻한 조명 아래 흰색과 겹친다. 그래서 이 넷은 **판정 조건을 좁게 잡아 잘 안 잡히게** 두었다. 셋 다 품종묘 색이라 한국 길고양이에서 거의 나오지 않아 실패 비용도 낮다.

**조명 보정** — 누끼 마스크로 배경 픽셀을 가려낼 수 있게 되면서, 배경의 저채도 픽셀로 색온도를 추정해 보정한다(gray-world). 잔디나 붉은 벽돌처럼 색이 강한 배경으로 보정하면 오히려 틀어지므로 채도 0.25 이하 픽셀만 쓰고, 표본이 부족하면 보정하지 않는다. 이득은 0.75~1.35로 제한한다.

**무늬 — 절대 색이 아니라 공간 구조로 판정한다.** 조명에 훨씬 덜 흔들린다.

| 무늬 | 판정 신호 |
|---|---|
| 태비 | 같은 색 영역 안의 주기적인 고주파 명암차(2픽셀 간격 밝기차 평균) |
| 원톤 | 두 번째 색 비율이 낮음 |
| 투톤 | 두 번째 색이 크고 연속된 덩어리(최대 연결 요소 비중 높음) |
| 토티 | 두 번째 색이 잘게 흩어짐 |

태비를 가장 먼저 본다. 같은 색 계열 안의 줄무늬(고등어 등)는 색 비율만으로는 원톤과 구분되지 않기 때문이다.

**초기 임계값은 실사진으로 조정이 필요한 값이다.** `coat-analysis.ts` 상단 상수에 모아 두었다.

**매칭 점수 영향** — 기존 "털색 힌트 일치 +0.08"은 이 두 축으로 나눠 배점을 다시 정해야 한다. **무늬 일치에 색보다 높은 가중치를 주는 것이 맞다.** 무늬가 조명에 덜 흔들려서 같은 개체를 다시 만났을 때 더 안정적인 신호다.

## 재설계 시 주의

- **RLS를 다시 짤 때 조심한다.** `000036_restore_profiles_authenticated_select`, `000037_restore_private_schema_usage`는 권한을 과하게 조였다가 되돌린 기록이다. 같은 실수를 반복하기 쉬운 지점이다.
- **테스트가 하나도 없다.** 재작성 시 회귀를 잡을 수단이 없으므로, 최소한 위 규칙들(희귀도 산정, 뱃지 임계값, 리더보드 점수)에 대한 테스트를 새로 깐다.
- **랜딩과 출시 알림 신청은 운영 중이다.** `docs/`와 `launch_waitlist` 관련 마이그레이션은 재설계 범위에서 제외한다.
